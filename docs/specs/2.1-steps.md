# Task 2.1 — Implementation steps

Breakdown of [2.1-read-only-ui.md](2.1-read-only-ui.md) into three steps.
Details live in the main spec; section, decision and check numbers below refer
to it. Each step ends with green `npm test` and `npm run typecheck` in the
`frontend` container and is committed separately after the file list is
approved.

## Step 1 — Frontend in Docker and API status

**Goal:** the page opens at `http://localhost:5173` and shows that it reaches
the API through the proxy.

**Scope:** generate the `react-ts` template in a one-off container and trim
it (§6); Vitest setup with the unstubbed-`fetch` guard (§7); `frontend`
service and volume (§4); proxy (D4); `api/client.ts` with `getHealth`;
`ApiStatus` (§5.1).

**Done when:**
- C1 and C2 pass.
- C3: `ApiStatus` tests for `ok`, non-`200` and network error. Each test is
  first seen failing on its assertion (component renders nothing yet), not on
  a missing module.
- C13: backend suite still green, no `backend/` files changed.

## Step 2 — Order table

**Goal:** the operator sees all orders with their sync state and can filter
and page through them.

**Scope:** `api/types.ts`, `getOrders`, `format.ts`, `OrderTable`, filter and
page state in `App` (§5.2, §5.4–5.6); fixtures for list responses.

**Done when:**
- C4, C5, C6 pass.
- C8 for the list (loading, error message, empty).
- C9 stale-response test.

## Step 3 — Detail panel and documentation

**Goal:** the operator opens an order and sees why it failed and every
attempt.

**Scope:** `getOrder`, `OrderDetail`, selection in `App` (§5.3); README
(§11).

**Done when:**
- C7 and C8 for the detail request.
- C10 read-only check, C11 determinism grep, C12 full frontend suite, C13.
- C14 manual check in the browser.
