# Task 1.3 — Sync logic and API

Status: accepted (P2–P5, P7 are defaults and may change in their step)
Depends on: 1.2 (data model, seeder; R9 rename applied)
Followed by: iteration 2 (React UI, read-only)

## 1. Goal

Make MerchantOps actually send orders to the simulated external service and
expose the result over a JSON API. After this task an operator (or `curl`) can
list orders, open one with its attempt history, send or retry it, and
configure the simulated failure for an order. Every send attempt is recorded
in `sync_attempts`, and the summary fields on `orders` always match that log.

Business context is described in 1.2 §1.1 and is not repeated here. In short:
orders already exist; MerchantOps only transfers them and records the result.

## 3. Accepted decisions

Decided before writing this spec. Numbers are referenced below.

| #  | Question | Decision |
|----|----------|----------|
| D1 | Meaning of `simulated_failures.remaining = 0` | Stays in the database and means "configured failure is used up, respond with success" (1.2 Q5). The API accepts only `remaining >= 1` or `null`; a failure is removed with `DELETE`. |
| D2 | Who keeps `orders` summary fields consistent with `sync_attempts` (1.2 Q7) | Only `OrderSyncService`, inside one database transaction that inserts the attempt and updates the order. A test checks the summary against the log. |
| D3 | Constraint on `external_order_id` (1.2 Q4(b)) | Two-way check in a new migration: `(sync_status = 'synced') = (external_order_id IS NOT NULL)`. |
| D4 | `POST /api/orders` | Not built. MerchantOps does not create orders. |
| D5 | HTTP status of a sync whose attempt failed (was P1) | `200` with the outcome in the body. Error statuses mean "no attempt was made" (404, 409, 422). Rejected: `502` (error status although data changed) and mirroring the external code (`401`, `422`, `429` would be read as errors of our own API). |

## 4. Simulated external service

`FakeExternalService::send(Order $order): ExternalServiceResponse`

The only class that reads or changes `simulated_failures`. It knows nothing
about attempts, triggers or order statuses.

`ExternalServiceResponse` is a small readonly class: either success with an
`externalOrderId`, or failure with a `SyncErrorCode`. Constructed only through
`ExternalServiceResponse::success(string $id)` and
`ExternalServiceResponse::failure(SyncErrorCode $code)`.

Decision table, evaluated against the order's `simulated_failures` row:

| Simulation row        | Response                  | Change to the row        |
|-----------------------|---------------------------|--------------------------|
| none                  | success                   | —                        |
| `remaining = null`    | failure with `error_code` | none                     |
| `remaining > 0`       | failure with `error_code` | `remaining - 1`          |
| `remaining = 0`       | success                   | none (D1)                |

On success the external ID is `EXT-<order number>`, e.g. `EXT-MO-0003` (P2).
It is derived from the order number, so it is unique (order numbers are
unique), deterministic and fits `varchar(64)`.

No randomness, no clock, no I/O other than the simulation row.

## 5. Sync operation

`OrderSyncService::sync(Order $order): Order`

Steps, all inside one `DB::transaction`:

1. Reload the order with `lockForUpdate()`. Concurrent syncs of the same order
   wait here and then see the state left by the first one.
2. If `sync_status = synced`, throw `OrderAlreadySyncedException`. Nothing is
   written.
3. Trigger: `initial` if `attempts_count = 0`, otherwise `retry`.
4. Call `FakeExternalService::send()`.
5. Insert a `sync_attempts` row:
   - success: `result = success`, error fields `null`;
   - failure: `result = failed`, `error_code`, and the snapshots
     `error_message = $code->message()`, `retryable = $code->retryable()`.
6. Update the order:

   | Field               | Success                  | Failure            |
   |---------------------|--------------------------|--------------------|
   | `sync_status`       | `synced`                 | `failed`           |
   | `external_order_id` | `EXT-<number>`           | unchanged (`null`) |
   | `last_error_code`   | `null`                   | the error code     |
   | `attempts_count`    | `+ 1`                    | `+ 1`              |
   | `last_attempt_at`   | attempt's `created_at`   | same               |

7. Return the fresh order.

Rules:

- `pending` and `failed` orders can be synced; `synced` cannot (409).
- Retrying a non-retryable error (`validation_failed`, `unauthorized`) is
  allowed. The API reports `retryable = false` so the UI can warn that the
  retry will fail again unless the cause is fixed (here: the simulation is
  removed).
- One timestamp is taken per attempt and used for both the attempt's
  `created_at` and the order's `last_attempt_at`.
- Any exception inside the transaction rolls back the attempt, the order
  update and the `remaining` decrement together.
- The service does not know the response came from a simulation.

## 6. API

All endpoints are under `/api`, accept and return JSON. Timestamps are ISO 8601
with offset. Money is integer `total_cents`. Unknown order ID → `404` with
`{"message": "..."}` (already JSON for `api/*`, see `bootstrap/app.php`).
Validation errors → `422` in Laravel's standard format
(`{"message": "...", "errors": {"field": ["..."]}}`).

| Method   | Path                                   | Purpose                               | Success |
|----------|----------------------------------------|---------------------------------------|---------|
| `GET`    | `/api/orders`                          | List orders, optional status filter   | 200     |
| `GET`    | `/api/orders/{order}`                  | Order with simulation and attempts    | 200     |
| `POST`   | `/api/orders/{order}/sync`             | Send or retry the order               | 200     |
| `PUT`    | `/api/orders/{order}/simulated-failure`| Set or replace the simulated failure  | 200     |
| `DELETE` | `/api/orders/{order}/simulated-failure`| Remove the simulated failure          | 204     |

### 6.1 Order fields

Shared by the list and the detail view.

```json
{
  "id": 3,
  "number": "MO-0003",
  "customer_name": "Grace Hopper",
  "total_cents": 3099,
  "currency": "EUR",
  "sync_status": "failed",
  "external_order_id": null,
  "last_error_code": "timeout",
  "last_error_retryable": true,
  "attempts_count": 1,
  "last_attempt_at": "2026-11-10T12:00:00+00:00"
}
```

`last_error_retryable` is `SyncErrorCode::retryable()` of `last_error_code`,
or `null` when there is no error. It is computed, not stored: it answers "will
a retry help now", while the attempt log keeps the classification at attempt
time.

### 6.2 `GET /api/orders`

Query parameters:

- `sync_status` — optional, one of `pending`, `synced`, `failed`; any other
  value → 422.
- `page` — optional, Laravel pagination.

Fixed page size 15, ordered by `id` ascending (P5). Response is Laravel's
paginated resource collection: `data` (array of §6.1), `links`, `meta`.
Attempts and simulation are not included in the list.

### 6.3 `GET /api/orders/{order}`

`data` is §6.1 plus:

```json
{
  "simulated_failure": { "error_code": "timeout", "remaining": 0 },
  "attempts": [
    {
      "id": 2,
      "trigger": "retry",
      "result": "success",
      "error_code": null,
      "error_message": null,
      "retryable": null,
      "created_at": "2026-11-10T12:01:00+00:00"
    },
    {
      "id": 1,
      "trigger": "initial",
      "result": "failed",
      "error_code": "timeout",
      "error_message": "External service did not respond in time.",
      "retryable": true,
      "created_at": "2026-11-10T12:00:00+00:00"
    }
  ]
}
```

- `simulated_failure` is `null` when the order has none. A used-up simulation
  (`remaining = 0`) is shown, so the operator can see why earlier attempts
  failed (D1).
- `attempts` are newest first: `created_at desc, id desc`. The `id`
  tie-breaker keeps the order stable when timestamps are equal (frozen time in
  tests).
- No pagination of attempts.

### 6.4 `POST /api/orders/{order}/sync`

No request body.

- Attempt performed (success **or** failure) → `200` with the §6.3 body. A
  failed attempt is a normal, recorded outcome of the operation, not an HTTP
  error (D5). The client reads `sync_status` and `attempts[0]`.
- Order already `synced` → `409` with
  `{"message": "Order is already synced."}`. No attempt is created, nothing
  changes.

### 6.5 `PUT /api/orders/{order}/simulated-failure`

Request:

```json
{ "error_code": "timeout", "remaining": 2 }
```

Validation:

| Field        | Rules                                                        |
|--------------|--------------------------------------------------------------|
| `error_code` | required, one of `SyncErrorCode` values                       |
| `remaining`  | must be present (P7); `null` or an integer `>= 1` (D1)        |

- Creates the row or replaces `error_code` and `remaining` of the existing one
  (one row per order, 1.2 §4.3).
- Response `200`: `{"data": {"error_code": "timeout", "remaining": 2}}`.
- Allowed for an order in any status (P3). For a `synced` order it has no
  effect, because such an order cannot be synced again.
- Validation failure → 422, the existing row is unchanged.

### 6.6 `DELETE /api/orders/{order}/simulated-failure`

- Deletes the row if it exists. Always `204` with an empty body, also when
  there was no row (P4).
- The next sync of the order succeeds.

## 7. Database change

New migration `*_add_external_order_id_check_to_orders_table.php`:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_external_order_id_check
  CHECK ((sync_status = 'synced') = (external_order_id IS NOT NULL));
```

`down()` drops the constraint. All seeded orders are `pending` with `null`
external ID, so the migration applies to the main database without data
changes. Existing migrations are not edited.

Time is frozen in tests where timestamps are asserted.

## 11. Manual scenario

On seeded data in the main database, after the user agrees (see R4):

```sh
# MO-0003: timeout once, then success
curl -X POST localhost:8000/api/orders/3/sync   # failed, timeout, retryable
curl -X POST localhost:8000/api/orders/3/sync   # synced, EXT-MO-0003
curl -X POST localhost:8000/api/orders/3/sync   # 409

# MO-0009: validation_failed forever, until the simulation is removed
curl -X POST localhost:8000/api/orders/9/sync   # failed, retryable=false
curl -X DELETE localhost:8000/api/orders/9/simulated-failure   # 204
curl -X POST localhost:8000/api/orders/9/sync   # synced

curl localhost:8000/api/orders/3                # 2 attempts, newest first
curl 'localhost:8000/api/orders?sync_status=failed'
```

IDs 3 and 9 match `MO-0003` and `MO-0009` only on a freshly seeded database.

## 12. Default decisions

Low-impact choices accepted with the recommended option without discussion.
Any of them may be changed in the step that implements it. P1 became D5.

| #  | Question | Options | Accepted |
|----|----------|---------|----------|
| P2 | Format of `external_order_id` | (a) `EXT-<number>`; (b) random/UUID | (a): deterministic, unique, readable. (b) violates the no-randomness rule |
| P3 | `PUT` simulation on a `synced` order | (a) allowed, no effect; (b) `409` | (a): simpler, harmless |
| P4 | `DELETE` without an existing simulation | (a) `204` (idempotent); (b) `404` | (a): the result "no simulation" is reached either way |
| P5 | List page size and order | (a) 15, `id` asc; (b) client-chosen `per_page` | (a): enough for 20 seeded orders to show two pages; no extra validation |
| P7 | Is `remaining` required in `PUT` | (a) must be present, `null` allowed; (b) optional, missing = `null` | (a): "fail forever" must be stated explicitly, not happen by omission |

## 13. Risks

| #  | Risk | Impact | Mitigation |
|----|------|--------|------------|
| R1 | Summary on `orders` drifts from `sync_attempts` | List shows wrong state | D2; C11; D3 catches the `synced`/ID part at DB level |
| R2 | Double sync under concurrent requests | Two attempts, inconsistent summary | `lockForUpdate` + status check inside the transaction. Real concurrency is not covered by PHPUnit tests; the lock is verified by review |
| R3 | Simulation leaks into sync logic | Service cannot be reused for a real integration | Only `FakeExternalService` reads `simulated_failures`; the service sees only `ExternalServiceResponse` |
| R4 | Manual check consumes demo data in the main DB | Seeded orders become `synced`; no way back except `migrate:fresh --seed`, which deletes data | Run §11 only with the user's consent; demo reset is iteration 4 |
| R5 | `PUT` simulation concurrent with a sync of the same order | `remaining` from one request overwrites the other | Accepted: manual operator tool; the sync's row lock on `orders` does not cover `simulated_failures` writes. Revisit if it matters |
| R6 | Equal timestamps in tests reorder attempts | Flaky order assertions | `id desc` tie-breaker (§6.3) |
| R7 | D3 breaks existing tests that create `synced` orders | Red suite after the migration | §9: `synced()` factory state, fix `DataModelTest` in the same step |
