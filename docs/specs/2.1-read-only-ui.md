# Task 2.1 — Read-only React UI

Status: draft
Depends on: 1.3 (JSON API)
Followed by: iteration 3 (UI actions: sync/retry, simulated failure management)

## 1. Goal

Give the operator a browser page for what the API already answers: which
orders are in which sync state, why a failed order failed, whether a retry can
help, and what happened on every attempt. The page only reads. Sending,
retrying and changing the simulation stay in `curl` until iteration 3.

Iteration 2 is this one task. It is split into steps in
[2.1-steps.md](2.1-steps.md).

## 2. Scope

### In scope

- New `frontend/` directory: React + TypeScript app built with Vite.
- `frontend` service in `docker-compose.yml`, Vite dev server on port 5173,
  `node_modules` in a named volume.
- Vite dev proxy `/api` → `backend` (D4).
- One page: API status, order table with status filter and pagination, order
  detail panel with simulation and attempt log (§5).
- Frontend tests with Vitest and React Testing Library (D3).
- README: Status, Getting started, Services, Tests.

### Out of scope

- Any write action: sync, retry, `PUT`/`DELETE` simulated failure — iteration 3.
- Statistics, filter by error code, creating orders — iteration 4.
- Backend changes of any kind, including CORS (D4).
- Production build and serving static files (no nginx). Only the dev server
  runs.
- Routing, URL state (filter and page in the address bar), state managers,
  data-fetching libraries, UI kits, CSS frameworks.
- Authentication.
- End-to-end browser tests.
- Responsive design beyond "usable on a laptop screen".

## 3. Accepted decisions

| #  | Question | Decision |
|----|----------|----------|
| D1 | Repository layout | `frontend/` next to `backend/` in the same repository. No workspaces, no root `package.json`, no monorepo tools. |
| D2 | Language and build tool | TypeScript (strict) with Vite, started from Vite's official `react-ts` template and trimmed. React and Vite at their current stable versions; exact versions pinned by `package-lock.json`. |
| D3 | Test tools | Vitest + React Testing Library (`@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`) + `jsdom`. No MSW: `fetch` is replaced with `vi.stubGlobal` and fixed fixtures. |
| D4 | How the browser reaches the API | Vite dev proxy. The browser calls `http://localhost:5173/api/...`; Vite forwards the request to `http://backend:8000` inside the Docker network. Same origin for the browser, so CORS is not involved and the backend does not change. |
| D5 | Iteration 2 boundaries | Read-only. The page issues only `GET` requests. |
| D6 | Where `npm` runs | Only inside the `frontend` container (`docker compose exec frontend npm ...`), like PHP. Node is not required on the host. |

## 4. Docker

New service in `docker-compose.yml`:

```yaml
frontend:
  image: node:24
  working_dir: /app
  command: sh -c "npm install && exec npm run dev"
  ports:
    - "5173:5173"
  volumes:
    - ./frontend:/app
    - node_modules:/app/node_modules
  depends_on:
    - backend
```

- No Dockerfile: the official image is enough (P1).
- `npm install` on every start mirrors `composer install` in the backend
  entrypoint: dependencies live in the `node_modules` volume and are brought
  up to date with `package-lock.json`.
- Vite listens on `0.0.0.0:5173` (`server.host`, `server.strictPort`), so it
  is reachable from the host.
- Proxy target comes from `API_PROXY_TARGET`, default `http://backend:8000`.
  It is a dev-server setting, not a secret, so it lives in `vite.config.ts`
  with that default and is not added to `.env`.
- The project is first generated with a one-off container
  (`docker compose run --rm --no-deps frontend ...`), because the service
  command needs `package.json` to exist.

## 5. Page

One page, no router. English UI text, like the rest of the project (P4).

```

│ MerchantOps                                       API: ok        │
├──────────────────────────────────────────────────────────────────┤
│ Status: [All ▾]                                                  │
│ ┌──────────────────────────────────────┐ ┌─────────────────────┐ │
│ │ Number  Customer  Total  Status  ... │ │ MO-0003  failed     │ │
│ │ MO-0001 ...                          │ │ Simulation: timeout │ │
│ │ MO-0003 ...  failed  timeout (retry) │ │ Attempts            │ │
│ │ ...                                  │ │ 12:00 initial failed│ │
│ └──────────────────────────────────────┘ │ ...                 │ │
│ ‹ Prev   Page 1 of 2   Next ›            └─────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

### 5.1 API status

`GET /api/health` once on page load. Shows `ok`, or `unavailable` when the
response is not `200` or the request fails. It is the first visible proof that
the browser → Vite → backend → database chain works.

### 5.2 Order table

`GET /api/orders?sync_status=<filter>&page=<n>`.

| Column | Source | Display |
|--------|--------|---------|
| Number | `number` | as is |
| Customer | `customer_name` | as is |
| Total | `total_cents`, `currency` | `Intl.NumberFormat`, e.g. `€30.99` |
| Status | `sync_status` | `pending` / `synced` / `failed` label |
| Last error | `last_error_code`, `last_error_retryable` | code with `retryable` or `not retryable`; empty when no error |
| Attempts | `attempts_count` | number |
| Last attempt | `last_attempt_at` | date and time (§5.5); empty when `null` |

- Status filter: `All`, `pending`, `synced`, `failed`. `All` sends no
  `sync_status`. Changing the filter resets the page to 1.
- Pagination: `Prev` / `Next` and `Page X of Y` from `meta.current_page` and
  `meta.last_page`. The client builds the next request itself and ignores the
  URLs in `links`/`meta.links`: they are absolute `http://localhost:8000/...`
  URLs that bypass the proxy (D4).
- Clicking a row selects the order and opens §5.3. The selected row is
  highlighted.

### 5.3 Order detail panel

`GET /api/orders/{id}` when an order is selected.

- Header: number, status, external order ID (when synced), customer, total.
- Simulated failure: `error_code` and `remaining` (`always` for `null`), or
  `none`. Labelled as the demo simulation, not order data (1.3 README "Key
  concepts").
- Attempt log, newest first as the API returns it: time, trigger, result,
  error code, error message, retryable. `No attempts yet` when empty.
- Closing the panel clears the selection. Changing filter or page keeps the
  panel open.

### 5.4 Loading, empty and error states

Each request (health, list, detail) has its own state:

- loading — a `Loading…` text; the previous content is not shown as current;
- error — `message` from the JSON body when present, otherwise
  `Request failed (<status>)`, or `Network error` when `fetch` rejects;
- empty — `No orders` for an empty list.

No automatic retry of failed requests and no polling.

### 5.5 Formatting

- Money: `Intl.NumberFormat('en-GB', { style: 'currency', currency })` on
  `total_cents / 100`. All seeded orders are `EUR`; currencies with other
  minor units are not handled (P3).
- Time: `Intl.DateTimeFormat('en-GB', { dateStyle: 'short', timeStyle: 'medium' })`
  in the browser's time zone. Tests run with `TZ=UTC`, so output is the same
  on every machine.

### 5.6 Stale responses

A response that arrives after the user has changed the filter, page or
selected order must not replace the newer data. Each effect aborts its
request with `AbortController` on cleanup; an aborted request does not show
an error.

### 6.1 Data flow

The code is grouped by kind in one level (`api/`, `components/`), with no
feature folders, service layers or stores. That is enough for one page and
three `GET` requests.

- `App` owns page state only: status filter, page number, selected order ID.
  It passes them down as props and receives changes through callbacks
  (`onFilterChange`, `onPageChange`, `onSelect`, `onClose`). It does not
  fetch.
- Each component fetches its own data from its props: `ApiStatus` on mount,
  `OrderTable` from `status` and `page`, `OrderDetail` from `orderId`. It
  keeps its own loading, error and empty state (§5.4) and aborts its own
  stale request (§5.6).
- Components call `api/client.ts` only; they never call `fetch` or build URLs.
- No custom hooks up front. If fetch logic starts repeating in iteration 3,
  it is extracted into a hook then.

Template leftovers (logos, counter demo, default styles) are removed. ESLint
from the template stays as generated (P2).

`.gitignore` covers `frontend/node_modules` and `frontend/dist` (the template's
own `.gitignore` already does).

## 7. Tests

- Run: `docker compose exec frontend npm test` (`TZ=UTC vitest run`).
- Tests never reach the backend or a database: any unstubbed `fetch` fails
  the test (setup file).
- Fixtures are hand-written, fixed data copied from the 1.3 §6 examples. No
  random data, no `Date.now()` in assertions.
- Components are tested through what the user sees (texts, roles), not
  internal state.
- `npm run typecheck` (`tsc --noEmit`) is part of "done", because Vitest does
  not type-check.

| C6  | Pagination | `Next` requests `page=2`; `Prev` disabled on page 1, `Next` disabled on the last page; request URL is relative (`/api/...`), never from `links` |
| C7  | Detail panel | Clicking a row requests `/api/orders/{id}` and shows header, simulation (`always` for `null`, `none` for absent) and attempts newest first; empty log shows `No attempts yet` |

| C12 | Frontend suite | `npm test` and `npm run typecheck` green in the container |
| C13 | Backend untouched | No files under `backend/` changed; `php artisan test` green |

## 10. Risks

| #  | Risk | Impact | Mitigation |
|----|------|--------|------------|
| R1 | TypeScript types drift from the API | UI reads a field that is not there | Types and fixtures follow 1.3 §6; C14 checks against the real API. Generated types are not worth it at this size |
| R2 | `node_modules` exists only in the volume | The editor on the host cannot resolve imports and shows type errors | Accepted; checks run in the container (D6). Revisit if it gets in the way |
| R3 | File watching through a macOS bind mount | Vite does not reload after edits | Docker Desktop forwards file events; if not, enable `server.watch.usePolling` |
| R4 | Absolute pagination URLs from Laravel | Following them bypasses the proxy and hits CORS | Client builds URLs itself (§5.2, C6) |
| R5 | Locale and time zone differ between machines | Flaky formatting tests | Fixed `en-GB` locale; `TZ=UTC` in the test script |
| R6 | First `npm install` in the volume is slow | Long first start | One-time cost; later starts are quick when the lock file is unchanged |
